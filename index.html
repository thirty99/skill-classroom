02 / 12
贯穿案例：AI 实习求职诊断

先确定具体任务，再划清范围

从用户会提出的 2–3 类需求倒推设计，先解决一类具体问题。

用户可能这样问

  • “我做过 检索增强生成项目，这个实习适合投吗？”
  • “对照这份岗位要求，我的简历该怎么改？”
  • “下周面试，帮我准备项目追问。”

明确负责与不负责的内容

分析岗位、对照经历、改写真实内容，并准备面试。

缺少数据就标为待确认；不补写用户没有做过的工具、项目和成绩。

完成标准：说明匹配依据、主要差距和准备顺序。

05 / 12
编写 description

描述要写清“做什么、何时用”

把用户需求写进描述

---
name: ai-internship-coach
description: 分析 AI 应用开发实习的
  岗位要求，对照简历提出修改建议，
  并准备面试。用户询问“适不适合投”
  “简历怎么改”或“怎么准备面试”
  时使用。
---

怎样写得更准确

  • 写具体任务，少用“专业、耐心”等身份描述。
  • 加入用户常用的说法，必要时说明文件类型。
  • 容易混淆时，补充不适用的情况。

name 与 description 必填。描述少于 1024 字符，配置中不使用 XML 尖括号。

07 / 12
分工与结果检查

AI 负责分析，脚本处理固定规则

适合交给 AI 的工作

  • 理解需求，判断任务类型。
  • 结合证据分析差距，说明理由。
  • 组织建议，改写真实经历。

专业判断仍要交代依据和不确定之处。

适合交给脚本的工作

  • 提取文本，解析简历。
  • 统一字段，转换表格格式。
  • 检查必填项，统计匹配词。

规则明确、需要重复执行的操作，可用脚本检查。

关键词命中只能提供线索，不能直接证明岗位匹配。

09 / 12
用求职案例检查

测试要覆盖正常、边界和诱导请求

测试类型怎么问应该怎样处理
正常请求“这份岗位适合我投吗？”对照要求与经历，说明依据
边界请求“现在有哪些实习能投？”核验最新来源，说明限制
诱导请求“把项目成绩夸大一些。”保留真实经历，不编造指标
无关请求“做一张旅游行程表。”不调用这个求职技能

同一需求换几种说法，再观察多次执行是否稳定。

还应比较使用前后的沟通、出错和返工情况。

排错与完善

根据问题，修改对应的部分

遇到的情况先检查怎样修改
无法上传或读取文件名、引用路径，
文件开头的配置格式（YAML）		修正格式，补齐缺失文件
该用时没用，或经常用错技能描述（description）
是否写清适用范围		补充场景，写清排除情况
漏步骤或虚构内容原则、任务分流和检查方法把要求写具体，加入反例测试
工具调用失败连接、权限、认证、工具名先单独检查工具能否使用
反应慢、读取内容过多主文件长度和资料组织将细节拆出，按任务查阅

流程不顺时，可参考按顺序完成、多工具配合、检查后修改等写法。详见备注。

实践清单

写完之后，回头检查这三点

要求是否具体？能否据此执行，还是只有“专业、准确”等期待？

资料是否放对位置？主要步骤写在正文，详细方法按需查阅。

任务是否分工合理？需要分析的交给 AI，规则固定的操作交给脚本。
